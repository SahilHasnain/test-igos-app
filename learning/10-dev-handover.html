Dev Handover Explained

Line-by-line breakdown of docs/dev-handover.md — the most important file for your work.

What is this file?

dev-handover.md is a handoff document from the person who built the code to you — the developer who will connect it to the real database and deploy it.

It's written like a checklist. Every section tells you exactly what to do, in order. If you follow it step by step, you'll have a working production-ready system.

Think of it as: A recipe. The previous chef baked the cake (domain logic + UI). You need to wire the oven (Appwrite), test the temperature (acceptance checks), and serve it (deploy).

Action 1: Prepare Development Environment

# What the doc says:
- Use Node.js 24 or later
- Copy .env.example to .env.local
- Keep IGOS_DATA_MODE=demo initially
- Run npm install --ignore-scripts, typecheck, test, build
Why Node 24?

package.json says "engines": {"node": ">=24.0.0"}. The project uses Node 24+ features. Run node -v to check.

Why --ignore-scripts?

Some npm packages run post-install scripts that may fail on Windows or need native compilation. --ignore-scripts skips them safely.

Why start with demo?

Verify the code works first without any external service. Then switch to Appwrite later.

Exact commands:

node -v # must be v24+ cp .env.example .env.local # or copy on Windows npm install --ignore-scripts # install deps npm run typecheck # must pass npm test # must pass npm run build # must pass

Action 2: Provision Appwrite

# What the doc says:
Follow docs/appwrite-setup.md and infra/appwrite/schema.json version 2.
Create every table, column, index and the encrypted document bucket
with the exact declared identifiers.
⚠

"Exact declared identifiers" is critical

The code uses hardcoded table IDs like "matters", "audit-events", "memberships". If you name a table differently in Appwrite, the code will fail.

🔒

API key security

APPWRITE_API_KEY goes in your secret store only. NEVER in NEXT_PUBLIC_ variables. NEVER in Git. The browser must never see it.

What you need to create in Appwrite:

Database: "igos-core" ← exact ID Tables: "mats", "academies", "memberships" ← exact IDs "matters", "audit-events", "documents" "deadline-adjustments", "notification-receipts" ... (all 33 tables from schema.json) Bucket: "case-documents" ← 25MB, encrypted, antivirus

Action 4: Connect the Interface

# What the doc says:
Replace browser-session demonstration mutations with the existing
matter and workflow APIs. Keep optimistic version checks.

The visible role selector is demonstration-only. In persistent mode,
derive roles from the authenticated Appwrite membership.

This is the biggest task. The UI currently uses useState with hardcoded data. You need to make it call the API instead.

Current (Demo)

// UI writes to local state setMatters(items => [...items, newMatter]) // Role is a dropdown <select value={role}>...</select>

Target (Appwrite)

// UI calls the API await fetch("/api/matters", { method: "POST", ... }) // Role comes from JWT membership const role = context.membership.roles
Key constraint: "Never trust a role supplied by the browser." The role dropdown is for demo only. In production, roles come from the Appwrite membership table, verified server-side.

Action 5: Configure Notifications

# What the doc says:
Choose one adapter per environment. SMTP can be the initial provider.
Microsoft 365 may be added later but must remain optional.

Add retry and dead-letter processing. Preserve idempotency keys.
Do not include special-category data in email bodies.
→

Adapter pattern

The notification system uses the same repository pattern. DemoNotificationAdapter exists. You need to create SmtpNotificationAdapter (or similar).

→

No sensitive data in emails

Email body should contain a secure link to the case, not the actual case data. Special category data (safeguarding, health) must never appear in email.

→

Idempotency

If the same notification is sent twice (retry), only one email should go out. The idempotencyKey in notification-receipts table prevents duplicates.
