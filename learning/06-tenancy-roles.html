Multi-Tenancy & Roles

How data isolation and access control work.

The Tenancy Model

MAT (Multi-Academy Trust) — Top-level tenant
│   Every row in every table has a matId column.
│   This is the FIRST isolation boundary.
│
├── Academy A (Riverside Academy)
│   │   Has academyId = "acad-a"
│   │
│   ├── Matters WHERE matId="X" AND academyId="acad-a"
│   ├── Documents WHERE matId="X" AND academyId="acad-a"
│   ├── DPIA sections WHERE matId="X" AND academyId="acad-a"
│   └── Users whose membership has academyId "acad-a" in academyIds[]
│
├── Academy B (Hillcrest Academy)
│   │   Has academyId = "acad-b"
│   │
│   ├── Matters WHERE matId="X" AND academyId="acad-b"
│   └── ...
│
└── Federation-wide
    │   Matters WHERE matId="X" AND academyId IS NULL
    │   (cross-academy scope)

Isolation Rules

Rule 1: matId Always Required

Every repository query MUST include Query.equal("matId", ...). This is enforced in every Appwrite adapter.

Rule 2: academyId When Scoped

If the user's membership has academyIds[], queries MUST also filter by Query.equal("academyId", ...).

Rule 3: Cross-MAT = Blocked

If a user from MAT "X" tries to access a matter from MAT "Y", the repository returns null — no error, no leak.

Rule 4: Server-Side Only

All Appwrite queries run server-side with an admin API key. The browser NEVER talks directly to Appwrite for data.

The 8 Roles

Defined in src/domain/model.ts

platform-admin

System-wide access across all MATs. Superuser.

mat-admin

Trust-level admin. Manages all academies in their MAT.

dpo

Data Protection Officer. Can approve, view audit, manage DPIAs.

case-manager

Creates and advances cases. Core operational role.

academy-lead

Academy-scoped admin. Sees only their academy's data.

contributor

Can contribute to cases (upload docs, add notes).

auditor

Read-only access to cases and audit trail.

read-only

View only. No create, update, or approve.

How Authorisation Works in Code

// src/domain/authorisation.ts

function capabilitiesFor(roles: Role[]): Capability[] {
  const caps = new Set<Capability>();
  for (const role of roles) {
    switch (role) {
      case "dpo":
        caps.add("matter:create");
        caps.add("matter:read");
        caps.add("matter:approve");
        caps.add("audit:read");
        // ...
      case "case-manager":
        caps.add("matter:create");
        caps.add("matter:read");
        caps.add("matter:update");
        // ...
    }
  }
  return [...caps];
}

// Service checks:
if (!hasCapability(context.membership.roles, "matter:create"))
  throw new Error("Insufficient permissions");

How to Seed Your First MAT Admin

From docs/appwrite-setup.md:

  1. Create an Appwrite user (first admin)
  2. Insert a row in mats table with status=active
  3. Insert academies in academies table linked to that MAT
  4. Insert a row in memberships linking the user → MAT with roles=["mat-admin","dpo"]
