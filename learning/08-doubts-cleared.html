Doubt #1 — Domain, Repository & Matter

What is a "Matter"?

In legal/governance language, a Matter = a case. That's it.

// src/domain/model.ts

interface Matter {
  id:              string;          // unique ID
  matId:           string;          // which trust owns this
  academyId?:      string;          // which academy (or null = federation-wide)
  reference:       string;          "SAR-2026-0178"  // human-readable ID
  type:            "sar" | "foi" | "breach" | "dpia"  // what kind of case
  status:          "draft" | "open" | ... | "closed"  // where in lifecycle
  title:           string;          // "Paula Leigh – pupil records"
  ownerUserId:     string;          // who is responsible
  statutoryDueAt?: string;          // deadline (SAR = +1 month, FOI = +20 days)
  version:         number;          // optimistic locking (prevents conflicts)
}
Real-world example: "Paula Leigh" submitted a Subject Access Request asking for all her child's school records. That request becomes a Matter with type "sar", a deadline, an assigned case manager, and documents attached to it.

What is "Domain"?

Domain = the business rules. Pure logic. No database. No UI. No framework. Just TypeScript functions that answer business questions.

domain/workflow.ts

Question it answers:

"Can this case move from 'evidence-gathering' to 'redaction'?"

// Defines every valid stage for each case type
sar: [intake → identity-verification → ... → closed]
foi: [intake → validity-check → ... → closed]
breach: [reported → containment → ... → closed]

// Defines what transition is allowed
findTransition("sar", "evidence-gathering", "redaction")
// → returns { from, to, capability: "matter:update" }

findTransition("sar", "evidence-gathering", "closed")
// → throws Error: "not permitted"

domain/deadlines.ts

Question it answers:

"When is this SAR due? When is this FOI due?"

SAR:   +1 calendar month (clamped to month-end)
FOI:   +20 working days (skips weekends + holidays)
Breach: +72 hours (cannot be paused)

// Real logic:
calculateDeadline(
  2026-01-31,   // received
  "sar-calendar-month"
)
// → 2026-02-28 (not March 3! Clamped to Feb end)

domain/authorisation.ts

Question it answers:

"Is this user allowed to do this?"

can(
  membership,    // { matId, academyIds, roles: ["dpo"] }
  scope,         // { matId: "X", academyId: "A" }
  "matter:create"  // what they want to do
)
// → true if dpo role has "matter:create"

domain/intake.ts

Question it answers:

"Is this SAR request form valid?"

// Zod schemas validate inputs
createSarInput.parse({
  title: "Paula Leigh – pupil records",
  academyId: "acad-riverside",
  requesterName: "Paula Leigh",
  requesterRelationship: "parent",
})
// → valid: proceeds

createSarInput.parse({
  title: "",   // too short!
})
// → throws ZodError: "title must be at least 3 chars"
Key point: Domain code has zero dependencies on Appwrite, Next.js, React, or any framework. It's pure TypeScript. That's why it has 19 test files — testing pure functions is trivial.

What is a "Repository"?

A Repository is a contract (interface) that says "here's what data operations I need". It doesn't care WHERE the data lives.

// src/repositories/matter-repository.ts — THE CONTRACT

interface MatterRepository {
  create(input): Promise<Matter>;
  findById(scope, id): Promise<Matter | null>;
  list(query): Promise<Matter[]>;
  update(scope, id, version, patch): Promise<Matter>;
}

Then two different teams implement this contract:

Team Demo

class DemoMatterRepository
implements MatterRepository {
  private matters = [] // JS array in memory
  create(input) { this.matters.push(...) }
  list(q) { return this.matters.filter(...) }
}

Data lives in a JavaScript array. Lost when you restart the server.

Team Appwrite

class AppwriteMatterRepository
implements MatterRepository {
  constructor(databases, dbId, tableId)
  create(input) { this.databases.createDocument(...) }
  list(q) { return this.databases.listDocuments(...) }
}

Data lives in Appwrite database. Permanent.

Analogy: Think of Repository like a car's steering wheel. The driver (Service) uses the steering wheel to turn. They don't care if the car is electric or petrol — the steering wheel works the same way. Repository is the steering wheel. Demo = electric car. Appwrite = petrol car. The Service just drives.

How They Work Together

// User clicks "Create new SAR" in the UI
         │
         ▼
API Route  POST /api/matters

MatterService.create(context, input)          ← src/services/matter-service.ts

Doubt #2 — How to Test Without Merging

Short Answer: Each PR is a separate Git branch you can run independently.

You don't need to merge to test. Each PR lives on its own branch. You checkout that branch, run the app, test it, and only merge when it passes.

How It Works Visually

main branch (Appsuite)  ─────────────────────────────────────
       │
       ├── PR #1 branch (igos-core-foundation)      ← checkout this, run & test
       │         │
       │         ├── PR #2 branch (igos-stage-2)   ← checkout this, run & test
       │         │         │
       │         │         ├── PR #3 branch (igos-stage-3)  ← checkout this
       │         │         │         │
       │         │         │         ├── PR #4 branch (igos-stage-4)  ← checkout this
       │         │         │         │         │
       │         │         │         │         ├── PR #5 branch (igos-stage-4b) ← checkout this
       │         │         │         │         │
       ▼         ▼         ▼         ▼         ▼
      Merge #1 → Merge #2 → Merge #3 → Merge #4 → Merge #5
      ⚠ ONLY after each one passes acceptance checks!

Step by Step — How to Test a PR

Step 1

Checkout the branch

git checkout agent/igos-core-foundation

Now your local files are PR #1's code. Not main. Not any other PR.

Step 2

Install & run

npm install --ignore-scripts && npm run dev

Opens on localhost:3000. This is PR #1 running.

Step 3

Test everything

Open the app, create SARs, advance workflows, check audit trail. All in demo mode. All self-contained.

Step 4

Run tests

npm run typecheck && npm test && npm run build

This is the CI gate. Must pass before merge.

Step 5

Only then merge

git checkout main && git merge agent/igos-core-foundation

After PR #1 merges, rebase PR #2 on top of main, then test PR #2, and so on.

Why Not Merge All at Once?

If You Merge All at Once

  • Bugs mix together — can't tell which PR broke what
  • If PR #3 has a critical bug, you can't undo just PR #3
  • Code review becomes impossible — too much change
  • Appwrite config might conflict between stages

If You Merge Sequentially

  • Each PR is tested in isolation before merge
  • If PR #2 breaks something, PR #1 still works
  • Easy to revert one stage without affecting others
  • Each merge is a clean, reviewable unit

The Actual Dev Workflow

Week 1: Work on PR #1
  git checkout agent/igos-core-foundation
  npm run dev                               ← test in browser
  npm test                                  ← run all tests
  ... fix bugs, add Appwrite adapters, test ...
  git push                                  ← updates the PR on GitHub
  ... open PR #1 for review ...

Week 2: Provision Appwrite dev, switch to appwrite mode
  IGOS_DATA_MODE=appwrite npm run dev      ← real DB
  ... test with real data ...
  ... run acceptance checks from dev-handover.md ...

When PR #1 passes:
  Merge PR #1 → main

Week 3: Work on PR #2
  git checkout agent/igos-stage-2-governance
  git rebase main                            ← get PR #1's changes
  npm run dev                                ← has DPIA, ROPA, Policies
  ... test, fix, push ...

When PR #2 passes:
  Merge PR #2 → main

... repeat for PR #3, #4, #5 ...
